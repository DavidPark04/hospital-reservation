# Backend

Java 21 · Spring Boot 3.5.16 · Gradle 8.13 기반 API입니다. `kr.dmu.hospital` 아래 `auth`, `member`, `integration`, `booking`, `common`, `config` 패키지를 사용합니다. 기능별 controller/service와 MongoTemplate으로 요청·저장·트랜잭션 흐름을 구성합니다.

## 실행

루트 `.env.example`의 변수명에 맞춰 환경변수를 준비합니다. Spring은 `.env`를 직접 읽지 않습니다. 루트 `scripts/start.mjs`는 로컬 설정을 읽어 Java 프로세스에 전달하며, 직접 실행할 때는 셸·IDE·배포 서비스에서 전달합니다. 비밀 값은 커밋하지 않습니다.

```bash
cd backend
./gradlew --no-daemon bootJar
java -jar build/libs/hospital-reservation.jar
```

Windows에서는 `gradlew.bat`을 사용합니다. 기본 API 주소는 `http://127.0.0.1:18081`, 상태 확인은 `/api/health`, OpenAPI UI는 `/swagger-ui.html`입니다. JWT_SECRET과 트랜잭션을 지원하는 MongoDB 연결이 필요합니다. MongoDB 단독 서버로는 예약·회원 삭제·가입·연락처 인증 증명 소모와 계정 변경 트랜잭션을 검증할 수 없습니다.

## 개인 이메일·문자 인증 설정

| 환경변수 | 용도 |
| --- | --- |
| `SMTP_USERNAME` | Gmail SMTP 발신 계정 |
| `SMTP_PASSWORD` | 해당 계정의 Gmail 앱 비밀번호. 서버의 무시된 로컬 설정 또는 배포 secret에만 저장 |
| `FIREBASE_API_KEY` | Firebase 웹 클라이언트 공개 API 키 |
| `FIREBASE_AUTH_DOMAIN` | 해당 프로젝트의 Firebase 인증 도메인 |
| `FIREBASE_PROJECT_ID` | 서버가 ID 토큰의 발급자·수신자를 검증할 Google Cloud/Firebase 프로젝트 ID |

Gmail은 `smtp.gmail.com:587`의 인증된 STARTTLS를 사용합니다. 이메일 코드는 5분, 최종 작업용 증명은 10분이며 발송 간격·횟수 제한을 서버에서 관리합니다. `/api/auth/verification/config`는 사용 가능 여부와 Firebase 공개 설정만 반환합니다. SMTP 앱 비밀번호는 브라우저·Git·응답·로그에 넣지 않습니다.

Identity Platform의 Phone 공급업체, 운영 주소의 승인 도메인, 실제 사용할 국가의 SMS 지역 정책이 필요합니다. 브라우저는 Firebase와 reCAPTCHA로 문자를 확인하고, 백엔드는 프로젝트에 서명된 최근 phone ID 토큰을 검증합니다. 서버용 Firebase 서비스 계정 비밀키를 요구하는 구조는 아닙니다. 테스트 전화번호는 실제 SMS를 보내지 않으므로 실제 수신 확인과 구분합니다. 로컬 개발은 프록시 전달 헤더를 신뢰하지 않으며, 배포 Docker는 신뢰하는 Vercel 프록시 뒤에서 `SERVER_FORWARD_HEADERS_STRATEGY=framework`를 사용합니다.

현재 외부 확인 범위: Gmail SMTP 인증 응답 `235`와 모의 API를 사용한 화면 검증을 확인했습니다. 운영 승인 도메인 추가와 테스트 번호 해제 상태를 확인했고, 한국(`KR`) 지역 정책 저장은 사용자가 완료했다고 알렸습니다. 실제 인증 메일·SMS의 수신과 실계정 전체 흐름은 별도 확인 대상입니다. 최종 자동 테스트·배포 결과는 해당 PR에 기록합니다.

## 테스트

앱 데이터베이스와 분리된 로컬 replica set에만 테스트를 실행합니다. 테스트는 고유 이름의 테스트 DB를 만들고 종료 시 그 DB만 제거합니다. 운영 Atlas URI를 `MONGODB_TEST_URI`로 지정하지 않습니다.

```bash
export MONGODB_TEST_URI='mongodb://127.0.0.1:27118/?replicaSet=hospital-rs'
./gradlew --no-daemon test bootJar
```

PowerShell에서는 `$env:MONGODB_TEST_URI='mongodb://127.0.0.1:27118/?replicaSet=hospital-rs'`로 설정합니다. 이 변수가 없으면 MongoDB 통합 테스트가 생략되므로 전체 통과로 보고하지 않습니다. GitHub Actions는 임시 MongoDB 8.0.16 replica set을 띄우고 테스트 생략이 없는지 확인합니다. 자동 테스트에 실제 OpenAI·HIRA·소셜 인증키는 사용하지 않습니다. 인증 회귀 테스트는 모의 발송기/검증기와 폐기 가능한 로컬 DB의 인증 증명을 사용하며 실제 이메일·SMS를 발송하지 않습니다.

## 구현과 제한

- 일반 회원은 이메일 대신 아이디로 로그인합니다. 비밀번호는 BCrypt로 저장합니다.
- 병원 계정은 사업자등록번호·비밀번호로 가입·로그인하며 이메일·소셜 로그인을 사용하지 않습니다. 개인의 기존 가입·소셜 로그인·마이페이지 기능은 유지합니다.
- `COMWEL_API_KEY`로 근로복지공단 사업장 정보를 조회하고 DB 병원명·주소 등과 대조합니다. 가입 확인값은 15분 동안 한 번만 사용합니다. 병원명·주소·우편번호·전화번호는 서버에서 확정하며 클라이언트가 보낸 수정값을 저장하지 않습니다. 전화번호가 없으면 빈칸입니다. 공개 정보 대조는 신청자의 실제 운영자 권한 인증과 다릅니다.
- 개인 일반 로그인 회원은 PATCH `/api/auth/password`에서 현재 비밀번호와 `PASSWORD_CHANGE` 문자 인증을 확인합니다. 관리자·병원 계정은 기존 비밀번호 확인 흐름을 유지합니다. 증명 소모·해시 교체·`tokenVersion` 증가를 원자적으로 처리하고 새 로그인 토큰을 반환합니다. 소셜 회원은 로컬 비밀번호를 생성·변경할 수 없습니다.
- 개인 일반·소셜 가입 완료에 `SIGNUP` 이메일·문자 인증이 필요합니다. 이메일 변경은 새 주소의 `EMAIL_CHANGE` 인증을 요구하고 이전 세션을 폐기합니다. 로그인 화면의 비밀번호 찾기는 LOCAL 개인 회원의 아이디와 등록 휴대전화 `PASSWORD_RESET` 인증으로 재설정한 뒤 다시 로그인합니다.
- 구글·카카오는 식별번호만 사용하고 이름·이메일·전화번호는 추가 입력으로 받습니다. 가입 완료 전 정보는 만료되는 임시 저장소에 보관합니다.
- 전화번호와 정규화 이메일 각각의 unique 인덱스로 이름과 무관하게 중복 가입을 막습니다. 기존 가입 방식은 `SIGNUP` 문자 인증을 서버가 검증한 뒤 인증된 번호와 일치하는 가입 완료 개인 USER가 있을 때만 성공 응답의 `existingAuthProvider`로 안내합니다. 이름·이메일을 비교하지 않으며 관리자·병원·미완료 소셜 계정과 다른 인증 목적은 안내 대상에서 제외합니다. 최종 가입의 연락처 중복은 가입 방식 없는 공통 409 안내를 유지하며 계정을 자동 연결하지 않습니다.
- 개인 회원 탈퇴는 등록 휴대전화의 `WITHDRAWAL` 문자 인증을 요구하고 LOCAL 회원은 현재 비밀번호도 확인합니다. 기존 소셜 OAuth 재확인 경로에도 문자 인증을 요구하여 우회하지 못합니다. 관리자·병원 계정은 개인 탈퇴 대상이 아닙니다.
- 관리자는 개인 회원과 병원 회원을 별도 목록에서 관리하고 삭제할 수 있으며 모든 관리자 계정은 삭제하지 못합니다. 병원 삭제는 소유 등록을 확인한 뒤 계정·등록 삭제, 의료진 비활성화, 일정 폐쇄, 병원 활성 예약 취소·자리 반환을 한 트랜잭션으로 처리합니다. 병원 기본 카탈로그와 의료진·일정·예약·이벤트 이력은 보존합니다. 같은 병원은 새 사업자 조회부터 다시 가입할 수 있으며 이전 의료진·일정은 자동으로 활성화하지 않습니다.
- 예약 생성·변경·취소와 관리자 회원 삭제·본인 탈퇴는 MongoDB 트랜잭션을 사용합니다. 탈퇴 시 인증 증명 소모·활성 예약 취소·정원 반환·요청 키 제거를 함께 처리합니다.
- 전체 병원 기본 자료는 MongoDB `hospitals`에 보관하고, 공개 검색·추천·상세·신규 예약은 `hospitalRegistrations`의 활성 등록 병원만 허용합니다. 웹 요청이 기본 공공 API 수집을 시작하지 않습니다. 기본 목록과 공공 진료과 분류는 월~토 한국 시간 00시의 요일별 지역 동기화에서 준비합니다. 주중 요청은 즉시 재시도하지 않고, 실패한 요청만 일요일 00시에 한 번 재처리합니다. 검증이 끝난 지역만 반영하며 미완성 지역과 대상 밖의 기존 병원 자료는 보존합니다.
- 선택한 병원의 진료과·특수진료·전문병원 지정 정보는 HIRA 상세 API를 필요할 때 조회하고, 완전한 결과는 1시간 재사용합니다. 선택한 병원만 보조 컬렉션 `hospitalDetails`에 상세 캐시로 저장하며 전국 기본 목록을 이 컬렉션에 복제하지 않습니다.
- 병원은 `/api/hospital/manage`에서 의료진·진료과·진료 일정·정원·휴진과 소속 병원의 예약을 관리합니다. 서버가 로그인 계정과 활성 병원 등록의 연결을 매번 확인하며 다른 병원 자료는 관리할 수 없습니다. 예약용 진료과는 병원이 등록한 활성 의료진 기준으로 공개합니다.
- 가상 의료진·시간표를 자동 생성하지 않고 병원이 직접 등록한 자료로 신규 예약을 받습니다. 기존 예약 이력은 유지합니다. 수업용 서비스이며 외부 병원 접수 시스템(HIS)에 연결하지 않으므로 앱의 예약 저장은 실제 접수 완료를 뜻하지 않습니다.
- 기본 관리자나 테스트 회원을 자동 생성하지 않습니다. `DEMO_ENABLED`는 샘플 병원 생성만 제어합니다.

API 필드·오류는 [API 계약](../docs/api-contract.md), 컬렉션·인덱스는 [DB 설계](../docs/database.md), Vercel 구성은 [배포 안내](../infra/README.md)를 따릅니다. 기본 목록 초기 적재와 요일별 지역 갱신은 [병원 목록 운영 안내](../docs/hospital-catalog.md)를 따릅니다. 자동 테스트는 고유 테스트 DB에 필요한 카탈로그 자료를 준비하며 운영 목록 전체를 수집하지 않습니다.
