# Hospital reservation implementation contract

Source: the 2026-11-20 report and subsequent signup requirements. React/TypeScript/Vite frontend and Spring Boot 3/Java 21 backend use a real MongoDB replica set. This repository integrates the local implementation and prepares Vercel deployment. Deployment success and real-account verification must be recorded separately from automated tests. Secrets and runtime data remain outside Git.

Java package `kr.dmu.hospital`. Use simple explicit feature controllers/services, no Lombok. JSON objects can use Map or org.bson.Document with String IDs (UUID), dates as ISO strings for responses, java.util.Date persisted. MongoTemplate available. Errors: `common.ApiException(int status, String message)` and JSON `{message}`. `auth.CurrentUser.require()` returns `UserPrincipal` with `getId(),getName(),getLoginId(),getRole()`; `CurrentUser.optional()` and `requireAdmin()` also exist. Spring Security JWT bearer authorization protects API requests. Public routes include hospital searches, metadata, chat, local signup/login, social provider discovery/exchange and OAuth authorization/callbacks. Other APIs authenticated; /api/admin/** ADMIN only. IDs always strings. Times UTC ISO; frontend displays Asia/Seoul.

## HTTP contract
- GET /api/meta -> {serviceName,model,virtualReservation:true,departments:[{code,name}],integrations:{openai:boolean,hira:boolean}}
- POST /api/auth/register {name,loginId,password,phone}, POST /api/auth/login {loginId,password} -> {token,user:User}. Phone is required for new signup, strips spaces/hyphens and accepts domestic 9–11 digits starting with 0; existing LOCAL members can sign in without a previously stored phone.
- Across LOCAL/GOOGLE/KAKAO, matching entered name plus normalized phone blocks a new signup and identifies the existing signup method (일반/카카오/구글). No SMS or email verification is required for this requested input-matching policy; it does not establish that the inputs belong to the same real person. No automatic account linking or profile/reservation merging occurs.
- A matching completed member returns HTTP 409 {message,code:'MEMBER_ALREADY_EXISTS',existingAuthProvider:'LOCAL'|'GOOGLE'|'KAKAO'}. UI messages identify the method only: "이미 카카오로 가입된 계정이 있어요. 카카오로 로그인해 주세요." or "이미 일반 가입으로 등록된 계정이 있어요. 아이디로 로그인해 주세요." They do not mention the matched name/phone. An unrelated loginId collision retains its existing message-only 409 response.
- User = {id,name,loginId,role,authProvider:'LOCAL'|'GOOGLE'|'KAKAO',profileComplete:boolean,emailVerified:false,email?,phone?}. Name/email/phone are entered by the user during first social signup; the email is not verified. A pending social response has name:'', loginId:'', profileComplete:false and no email/phone; its id identifies a temporary signup authorization, not a users member. No provider subject, credential, token or image fields in User. Local login IDs normalize to lowercase and remain separate from internal IDs.
- GET /api/auth/me -> User
- GET /api/auth/social/providers -> {providers:[{id:'google'|'kakao',enabled:boolean,authorizationUrl:string}]}
- GET /oauth2/authorization/{provider} starts OAuth; GET /login/oauth2/code/{provider} is the provider callback. Spring Security validates authorization state; Google uses OIDC.
- Successful social login redirects to the frontend /auth/social/callback with a short-lived HttpOnly exchange cookie, never a JWT in the URL. POST /api/auth/social/exchange returns {token,user:User} once. First-time social authentication creates a temporary signup authorization only; it does not insert a users member. Its SIGNUP-purpose JWT allows status lookup, signup completion and logout, but not member functions.
- POST /api/auth/social/profile {name,email,phone} requires a live temporary signup JWT and returns {token,user:User}. All three fields are required. After validation and duplicate checks, one MongoDB transaction inserts a completed users member with a fresh member ID and consumes the temporary authorization. The response contains a regular MEMBER-purpose token. The old signup token cannot authenticate or become a member token; a completed member repeating the endpoint receives 409. Other client-supplied role, ID or verification fields are ignored. Afterwards the frontend goes to the allowed return page or /mypage.
- GET /api/admin/members -> {items:[{id,name,loginId,role,authProvider,profileComplete:true,email?,phone?,createdAt}]}; newest first, ADMIN only. It returns completed members only: LOCAL or missing/null authProvider legacy users, and GOOGLE/KAKAO users with Boolean profileComplete=true. Temporary signup authorizations and any legacy pending social users are excluded.
- DELETE /api/admin/members/{id} -> {message,deletedUserId,canceledReservations}; protects all ADMIN accounts and atomically removes a USER, cancels active reservations, restores capacity and clears request keys.
- POST /api/auth/logout -> {message}; client removes token. A regular member's token version is revoked; a temporary signup authorization is deleted without creating a member.
- GET /api/hospitals?query=&region=&department= -> {items:[Hospital],source:'LIVE'|'CACHE'|'SAMPLE',message?,fetchedAt?}
- GET /api/hospitals/{id} -> Hospital (with evidence and departments)
- Hospital = {id,name,address,tel,departmentCode?,departmentName?,departments?:[{code,name}],evidence?:[{kind,label,value,sourceUrl,basePeriod?,fetchedAt}],source:'LIVE'|'CACHE'|'SAMPLE',fetchedAt,latitude?,longitude?}
- POST /api/chat {messages:[{role:'user'|'assistant',content:string}],region?:string} -> {reply,hospitals:Hospital[],departmentCode?,departmentName?,needsMoreInfo:boolean,emergency:boolean,mode:'AI'|'FALLBACK',source?,notice?}. AI never invents hospitals; query HIRA server-side. No symptom persistence. gpt-6.2-sol Responses API.
- GET /api/hospitals/{id}/doctors?department=01 -> {items:[Doctor]}; doctors persisted once per hospital+department and reused.
- Doctor = {id,hospitalId,departmentCode,name,specialty,isVirtual:true}
- GET /api/slots?doctorId=&date=YYYY-MM-DD -> {items:[Slot]}
- Slot = {id,doctorId,startAt,capacity,reservedCount,remaining,closed}
- POST /api/reservations {slotId} + Idempotency-Key header -> Reservation
- GET /api/reservations -> {items:[Reservation]}
- PATCH /api/reservations/{id} {slotId} + Idempotency-Key -> Reservation
- DELETE /api/reservations/{id} + Idempotency-Key -> Reservation (CANCELED)
- Reservation = {id,status:'RESERVED'|'CANCELED',startAt,slotId,doctorId,hospitalId,hospitalName,departmentName,doctorName,createdAt}
- GET /api/admin/slots?doctorId=&date= -> {items:[Slot]}
- POST /api/admin/slots {doctorId,date,startTime,endTime,intervalMinutes,capacity} -> {items:[Slot]}
- PATCH /api/admin/slots/{id} {capacity,closed} -> Slot (reject capacity below existing reservations; closing reserved slot rejects with explanatory 409).

## Persistence / consistency
Collections users, hospitals, hospitalEvidence, doctors, timeSlots, reservations, requests, reservationEvents, social_signups, oauth_authorization_requests, social_login_tickets and chat_usage. MongoDB conditional capacity update + multi-document transactions, per-user idempotency key unique and request hash mismatch=409, active reservation unique(userId,startAt), cancel returns capacity once, change rolls back on failure. Reference IDs/owners checked. Existing/sample hospitals explicitly labelled; fallback never falsely presented as actual API/AI response. `DEMO_ENABLED` seeds sample hospitals only; no default/demo user or administrator is created. The requested `admin` account was provisioned separately.

Completed social users are keyed by `socialIdentity` (provider plus subject) with a unique partial index; repeated sign-ins reuse that same user and preserve manually entered profile data. Provider name/email/image attributes are not saved. Before completion, `social_signups` stores only the provider identity, temporary ID, createdAt, expiresAt and tokenVersion; it has a unique socialIdentity index and a 30-minute expiry with a TTL index. Each authentication checks expiresAt directly rather than waiting for TTL cleanup. Reauthentication increments tokenVersion, so extending temporary expiry cannot revive a prior signup JWT. Completion inserts users fields authProvider, socialSubject, socialIdentity, generated loginId, name, email, phone, emailSource:'USER', emailVerified:false, profileComplete:true and profileCompletedAt, and atomically consumes the temporary authorization. Generated login IDs are not email addresses. New social users always have role USER and no local password. No automatic linking by email, no provider access/refresh token persistence, and no provider tokens or subjects in public/member responses. Legacy local users without authProvider are shown as LOCAL and complete; social users are complete only when profileComplete is Boolean true.

Completed members with usable name/phone claim `memberIdentityClaimed:true` and `nameNormalized` (NFC, trim, collapse internal whitespace to one space, Locale.ROOT lowercase). A partial unique compound index `user_name_phone_v1` on (nameNormalized,phone) prevents concurrent cross-provider completion. Startup backfills existing completed members; existing duplicate keys stop initialization without deleting or merging accounts. Legacy admin without phone is excluded. Pending social users do not claim the name/phone pair.

Startup migrates legacy users records only when role=USER, authProvider is GOOGLE/KAKAO and profileComplete is not Boolean true. Reservation, request and reservation-event references are checked before migration; any references stop initialization and preserve the records. A valid provider identity is copied into temporary social_signups and its legacy pending users document removed within one transaction. Completed members and admins are excluded. Old pending member JWTs cannot authenticate after this transition; the user must authenticate with the provider again.

`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `KAKAO_CLIENT_ID` (REST API key), `KAKAO_CLIENT_SECRET` stay in ignored local settings or server-side deployment environment variables. Google requests openid only; Kakao requests no additional personal-data scope and does not need business-app/email permission for this design. Both providers are used only for stable account identity, while name/email/phone are collected by our signup form. `APP_FRONTEND_URL` defaults to http://127.0.0.1:5174 and `APP_BACKEND_URL` to http://127.0.0.1:18081. Both use the same hostname for the exchange cookie. Vercel deployment uses HTTPS service URLs and exact registered callbacks while retaining local callbacks. Frontend and backend routes share the production origin. See the deployment guide for configuration and verification status.

## Frontend
Korean, calm teal/blue hospital product. All real behavior connected to /api (Vite proxy 18081). Pages main/search, consultation, hospital detail/booking, my reservations, admin, login/register. Accessible, responsive. User sees simulation indicator and evidence source/date. Friendly loading/errors/empty state. TanStack Query. No fake successful booking or silent API fallback. No secrets in frontend. No requirement to use generated images.

## Shared deployment state

`oauth_authorization_requests` stores only required OAuth protocol fields with a five-minute expiry; state and browser binding are SHA-256 hashes. Google nonce/PKCE fields are restored for Spring validation. The `hospital_oauth_binding` cookie is HttpOnly, Secure for HTTPS, SameSite=Lax, path `/login/oauth2/code`, max age 300 seconds. `social_login_tickets` has a 60-second expiry. Both collections have zero-second expiresAt TTL indexes and use expiry predicates with atomic findAndRemove, so a different service instance can finish the flow without replay. Provider access/refresh tokens and personal profile attributes are not persisted.

`chat_usage` stores an HMAC-SHA256 key derived from JWT_SECRET, the KST calendar date and caller identity, a count and expiry at the next KST midnight. It shares the existing daily limits of 20 anonymous/60 authenticated calls across instances using conditional atomic increments. It stores no original IP, user ID or symptom text; the former JVM-map key-count limit is removed.
