# Hospital reservation implementation contract

Source: the 2026-11-20 report and subsequent signup requirements. React/TypeScript/Vite frontend and Spring Boot 3/Java 21 backend use a real MongoDB replica set. This repository integrates the local implementation and prepares Vercel deployment. Deployment success and real-account verification must be recorded separately from automated tests. Secrets and runtime data remain outside Git.

Java package `kr.dmu.hospital`. Use simple explicit feature controllers/services, no Lombok. JSON objects can use Map or org.bson.Document with String IDs (UUID), dates as ISO strings for responses, java.util.Date persisted. MongoTemplate available. Errors: `common.ApiException(int status, String message)` and JSON `{message}`. `auth.CurrentUser.require()` returns `UserPrincipal` with `getId(),getName(),getLoginId(),getRole()`; `CurrentUser.optional()` and `requireAdmin()` also exist. Spring Security JWT bearer authorization protects API requests. Public routes include hospital searches, metadata, chat, local signup/login, verification configuration, purpose-checked email/phone verification, password reset, social provider discovery/exchange and OAuth authorization/callbacks. Other APIs authenticated; /api/admin/** ADMIN only. IDs always strings. Times UTC ISO; frontend displays Asia/Seoul.

## HTTP contract
- GET /api/meta -> {serviceName,model,virtualReservation:true,departments:[{code,name}],integrations:{openai:boolean,hira:boolean}}
- POST /api/auth/register {name,loginId,password,email,phone,emailVerificationToken,phoneVerificationToken}, POST /api/auth/login {loginId,password} -> {token,user:User}. Email and mobile phone plus matching SIGNUP proofs for both channels are required for new personal signup. Hospital signup is unchanged. Phone strips spaces/hyphens and accepts domestic 9–11 digits starting with 0. Email is stored trimmed, with trim + Locale.ROOT lowercase in emailNormalized for comparisons. Existing LOCAL members can sign in without a previously stored contact; missing legacy values are not fabricated.
- Across LOCAL/GOOGLE/KAKAO, either a matching normalized phone or email blocks a new signup regardless of name. Final local registration and social profile completion return HTTP 409 {message:'이미 가입된 정보가 있어요. 기존에 가입한 방법으로 로그인해 주세요.',code:'MEMBER_ALREADY_EXISTS'} for contact duplicates, without provider information. Names do not affect blocking or signup-method disclosure. No automatic account linking or profile/reservation merging occurs.
- Only a successful SIGNUP phone confirmation may disclose existingAuthProvider:'LOCAL'|'GOOGLE'|'KAKAO', after the server verifies the Firebase token and finds a completed personal USER with the verified phone. Never select an account by client-supplied phone, name or email. Exclude ADMIN, HOSPITAL and pending social accounts; other purposes and email confirmation omit this field. Both signup forms keep the returned proof and locked verified phone, immediately show the matching login action and block signup completion. UI messages identify the method only: "이미 카카오로 가입된 계정이 있어요. 카카오로 로그인해 주세요.", "이미 구글로 가입된 계정이 있어요. 구글로 로그인해 주세요." or "이미 일반 가입으로 등록된 계정이 있어요. 아이디로 로그인해 주세요." The social form ends its temporary signup authorization when the user chooses that login action. No existing member ID, name, email or login ID is returned. There is no separate signup-information lookup API or screen. An unrelated loginId collision retains its existing message-only 409 response.
- User = {id,name,loginId,role,authProvider:'LOCAL'|'GOOGLE'|'KAKAO',profileComplete:boolean,emailVerified:boolean,phoneVerified:boolean,email?,phone?}. Name/email/phone are entered by the user during first social signup; both contacts are verified before completion. Newly completed personal members have both flags true. Missing/false legacy verification flags are not automatically upgraded. A pending social response has name:'', loginId:'', profileComplete:false and no email/phone; its id identifies a temporary signup authorization, not a users member. No provider subject, credential, token or image fields in User. Local login IDs normalize to lowercase and remain separate from internal IDs.
- GET /api/auth/me -> User
- PATCH /api/auth/password {currentPassword,newPassword,phoneVerificationToken} -> {token,user:User}; completed LOCAL personal USER requires a matching PASSWORD_CHANGE phone proof. LOCAL ADMIN and HOSPITAL retain the existing password-only request. Both password values preserve spaces. Verify the current BCrypt password, require a different new password of at least 8 characters and at most 72 UTF-8 bytes, and atomically consume the USER phone proof, replace passwordHash and increment tokenVersion only if the authenticated version and old hash still match. Incorrect current password or invalid new value returns 400 without revoking the current session; missing/expired authentication is 401 and social/pending access is denied. The frontend validates its confirmation field, replaces the stored JWT with the returned token and clears the password fields. Previous JWTs no longer authenticate; no local password is added to social accounts.
- GET /api/auth/verification/config -> {emailEnabled,phoneEnabled,firebase:{apiKey,authDomain,projectId}}. Public client configuration only; never SMTP credentials.
- POST /api/auth/verification/email/send {purpose,email} -> {challengeId,expiresIn:300,retryAfter:60}; purpose SIGNUP or EMAIL_CHANGE. POST /api/auth/verification/email/confirm {challengeId,code} -> {verificationToken,expiresIn:600,contact}. Gmail delivers a six-digit code, valid for five minutes with at most five confirmation attempts. Per normalized email, resend cooldown is 60 seconds and the fixed 15-minute quota is five attempts; per request IP the quota is 20. Limit failures return 429, invalid/missing/expired proofs 400, unavailable SMTP 503.
- Browser Firebase Phone Auth and reCAPTCHA send/check SMS. POST /api/auth/verification/phone/confirm {purpose,idToken,loginId?} validates the signed Firebase token and returns HTTP 200 {verificationToken,expiresIn:600,contact,existingAuthProvider?}. The optional provider field applies only to the SIGNUP disclosure rule above. Purposes are SIGNUP, PASSWORD_CHANGE, WITHDRAWAL and PASSWORD_RESET; reset also requires loginId matching a LOCAL USER and its stored phone. Verify the configured project, issuer, audience, RS256 signature, expiry, phone provider, no tenant and auth_time within five minutes. Accept Korean mobile numbers only. A Firebase session does not sign the user into MediPick.
- SIGNUP verification is anonymous or bound to a live pending social signup. EMAIL_CHANGE, PASSWORD_CHANGE and WITHDRAWAL require a completed USER JWT. PASSWORD_RESET is public but bound to the matching stored LOCAL USER. Proof scope includes purpose, channel, normalized contact, user/pending ID and tokenVersion. Final writes consume proofs in the same MongoDB transaction and roll back consumption when the write fails.
- PATCH /api/auth/email {email,emailVerificationToken} -> {token,user:User}; completed personal USER with EMAIL_CHANGE proof for the new address. Reject unchanged email (400) or duplicate email (409). Atomically update email/emailNormalized/emailVerified and increment tokenVersion. The frontend replaces its session; all previous JWTs are invalid.
- POST /api/auth/password/reset {loginId,newPassword,phoneVerificationToken} -> {message}; LOCAL personal USER only, with a matching PASSWORD_RESET proof. Atomically consume the proof, replace the hash, set phoneVerified and increment tokenVersion. Revoke old sessions and return to login without automatic sign-in. ADMIN, HOSPITAL and social accounts are excluded.
- DELETE /api/members/me {password?,phoneVerificationToken} -> {message,deletedUserId,canceledReservations}; completed USER with matching WITHDRAWAL phone proof; LOCAL also requires its current password. The retained social OAuth routes /api/auth/social/withdrawal/start, /confirm and /cancel remain available. /confirm additionally requires the same phoneVerificationToken along with its original JWT and HttpOnly OAuth proof cookie; OAuth alone cannot bypass SMS. Member deletion, proof consumption, reservation cancellation and request/ticket/proof cleanup share one transaction.
- GET /api/auth/social/providers -> {providers:[{id:'google'|'kakao',enabled:boolean,authorizationUrl:string}]}
- GET /oauth2/authorization/{provider} starts OAuth; GET /login/oauth2/code/{provider} is the provider callback. Spring Security validates authorization state; Google uses OIDC.
- Successful social login redirects to the frontend /auth/social/callback with a short-lived HttpOnly exchange cookie, never a JWT in the URL. POST /api/auth/social/exchange returns {token,user:User} once. First-time social authentication creates a temporary signup authorization only; it does not insert a users member. Its SIGNUP-purpose JWT allows status lookup, SIGNUP email/phone verification, signup completion and logout, but not member functions.
- POST /api/auth/social/profile {name,email,phone,emailVerificationToken,phoneVerificationToken} requires a live temporary signup JWT and returns {token,user:User}. All profile fields and both SIGNUP proofs are required. After validation and duplicate checks, one MongoDB transaction inserts a completed users member with a fresh member ID and consumes both contact proofs and the temporary authorization. The response contains a regular MEMBER-purpose token. The old signup token cannot authenticate or become a member token; a completed member repeating the endpoint receives 409. Client-supplied role, ID or verification-status booleans cannot override server decisions. Afterwards the frontend goes to the allowed return page or /mypage.
- GET /api/admin/members -> {items:[{id,name,loginId,role,authProvider,profileComplete:true,email?,phone?,createdAt,hospitalId?,businessNumber?}]}; newest first, ADMIN only. It returns completed members only: LOCAL or missing/null authProvider legacy users, and GOOGLE/KAKAO users with Boolean profileComplete=true. Temporary signup authorizations and any legacy pending social users are excluded. Only HOSPITAL items include hospitalId and businessNumber. The UI separates personal (USER/ADMIN) and hospital (HOSPITAL) tabs; hospital rows show business number and phone, and all ADMIN rows remain protected from deletion.
- DELETE /api/admin/members/{id} -> {message,deletedUserId,canceledReservations}; ADMIN only and protects all ADMIN accounts. USER deletion atomically removes the account, cancels active reservations, restores capacity and clears request keys. HOSPITAL deletion verifies the registration's hospital ID, owner and business number against the account, then atomically removes the account/registration and related request/verification records, disables its doctors, closes its slots and cancels its RESERVED reservations with capacity release and CANCEL events attributed to the administrator. A missing or mismatched registration returns 409 without partial deletion. Keep the base hospital catalog, doctor/slot documents and reservation/event history. Removing the registration releases the hospital/business-number uniqueness claims so a fresh business verification can start a new signup; old doctors/slots stay inactive/closed. A hospital cannot use personal self-withdrawal.
- POST /api/auth/logout -> {message}; client removes token. A regular member's token version is revoked; a temporary signup authorization is deleted without creating a member.
- GET /api/hospitals?query=&region=&department= -> {items:[Hospital],source:'CACHE'|'SAMPLE',message?,fetchedAt?}. Query active hospitals documents only, use departmentCodes for department membership, and return at most 30 rows sorted by name and ID. No HIRA basic API call on a web request. Sample search from hospitalDetails is allowed only when the catalog is empty and DEMO_ENABLED=true.
- GET /api/hospitals/{id} -> Hospital (with evidence and departments). Overlay current catalog basic fields on the selected-hospital detail cache. Missing catalog ID=404; active=false=410, with explicitly stored sample details kept separate. Fetch department/special-care/specialist-designation details on demand and reuse complete results for one hour. Do not expose apiFields, externalId or content hashes.
- Hospital = {id,name,address,tel,departmentCode?,departmentName?,departments?:[{code,name}],evidence?:[{kind,label,value,sourceUrl,basePeriod?,fetchedAt}],source:'LIVE'|'CACHE'|'SAMPLE',fetchedAt,latitude?,longitude?}
- POST /api/chat {messages:[{role:'user'|'assistant',content:string}],region?:string} -> {reply,hospitals:Hospital[],departmentCode?,departmentName?,needsMoreInfo:boolean,emergency:boolean,mode:'AI'|'FALLBACK',source?,notice?}. AI never invents hospitals; select candidates from the same MongoDB catalog search without calling the basic HIRA API. No symptom persistence. gpt-6.2-sol Responses API.
- GET /api/hospitals/{id}/doctors?department=01 -> {items:[Doctor]}; doctors persisted once per hospital+department and reused.
- Doctor = {id,hospitalId,departmentCode,name,specialty,isVirtual:true}
- GET /api/slots?doctorId=&date=YYYY-MM-DD -> {items:[Slot]}
- Slot = {id,doctorId,startAt,capacity,reservedCount,remaining,closed}
- POST /api/reservations {slotId} + Idempotency-Key header -> Reservation
- GET /api/reservations -> {items:[Reservation]}
- PATCH /api/reservations/{id} {slotId} + Idempotency-Key -> Reservation
- DELETE /api/reservations/{id} + Idempotency-Key -> Reservation (CANCELED)
- Reservation = {id,status:'RESERVED'|'CANCELED',startAt,slotId,doctorId,hospitalId,hospitalName,departmentName,doctorName,createdAt}
- GET /api/admin/slots?doctorId=&date= -> {items:[Slot]}
- POST /api/admin/slots {doctorId,date,startTime,endTime,intervalMinutes,capacity} -> {items:[Slot]}
- PATCH /api/admin/slots/{id} {capacity,closed} -> Slot (reject capacity below existing reservations; closing reserved slot rejects with explanatory 409).

## Persistence / consistency
Collections users, hospitals, hospitalEvidence, doctors, timeSlots, reservations, requests and reservationEvents retain the report's core names. Additional collections are hospitalDetails, hospitalImportRuns, social_signups, oauth_authorization_requests, social_login_tickets, social_withdrawal_proofs, chat_usage, contactVerificationChallenges, contactVerificationProofs, contactVerificationLimits and phoneVerificationReceipts. MongoDB conditional capacity update + multi-document transactions, per-user idempotency key unique and request hash mismatch=409, active reservation unique(userId,startAt), cancel returns capacity once, change rolls back on failure. Reference IDs/owners checked. Existing/sample hospitals explicitly labelled; fallback never falsely presented as actual API/AI response. `DEMO_ENABLED` seeds sample hospitals only; no default/demo user or administrator is created. The requested `admin` account was provisioned separately.

hospitals owns basic HIRA data, matching the report's hospital collection, and preserves every raw basic field in apiFields. IDs match UUID.nameUUIDFromBytes(UTF-8("HIRA:" + ykiho)), with provider/externalId uniqueness. departmentCodes comes from basic-list department filters rather than a nationwide detail crawl. Weekly regional GitHub Actions runs are scheduled at 00:00 Asia/Seoul on Monday through Saturday: Seoul; Gyeonggi; Busan/Jeonnam-Gwangju/Gyeongnam; Daegu/Incheon/Gyeongbuk; Jeonbuk/Chungnam/Daejeon; Chungbuk/Gangwon/Ulsan/Jeju/Sejong/legacy Gwangju respectively. Sunday at 00:00 retries only failed requests from the same week's weekday batches once; another failure ends that week's attempt. Seven distinct cron entries at 15:00 UTC on the preceding day preserve the intended weekday after delays or reruns. Manual dispatch explicitly selects a weekday collection group or Sunday retry mode. Retry mode runs only on an actual KST Sunday; weekday collection is skipped on Sundays. Runs outside these mode/day boundaries skip before network access or DB claims. Weekday data requests use fixed 500-row pages, with no immediate retry or smaller-page fallback. Successful responses and failed request metadata are retained as key-free GitHub artifacts for 14 days. Sunday reuses successful cached responses, calls only recorded failures and does not fetch previously unattempted requests. Atomic week/day/mode claims in hospitalImportRuns prevent duplicate processing. A region is applied only when all its basic and department scopes are complete and valid; incomplete regions and unrelated regions retain their existing DB records. Only new or changed hospital documents are written, and only hospitals missing from a successfully scanned region may be marked inactive. Account/reservation data is preserved. Recovery-only schema 4 permits same-week checkpoints up to eight days old and validation/application within 48 hours of Sunday completion, with identical completedAt and recoveredAt values; it does not permit new retry requests after Sunday. Ordinary schemas 1/2/3 retain the 48-hour limit. Per-region current/high-water records prevent stale reapplication, including cross-region moves, while existing nationwide records remain full-snapshot baselines. A delayed or failed schedule does not trigger collection on user requests. See [catalog operations](hospital-catalog.md) for exact commands, validation and recovery.

The additional hospitalDetails collection materializes only selected hospitals for detail caching and existing booking references, using the same hospital IDs as hospitals. Do not copy the entire hospitals catalog into hospitalDetails/hospitalEvidence or repeat per-hospital backfill for the nationwide catalog at startup. Inactive hospitals reject new doctor/slot access and reservation creation/change, while existing reservation history and cancellation remain available. Base-information changes do not erase detail evidence or change hospital IDs.

Completed social users are keyed by `socialIdentity` (provider plus subject) with a unique partial index; repeated sign-ins reuse that same user and preserve manually entered profile data. Provider name/email/image attributes are not saved. Before completion, `social_signups` stores only the provider identity, temporary ID, createdAt, expiresAt and tokenVersion; it has a unique socialIdentity index and a 30-minute expiry with a TTL index. Each authentication checks expiresAt directly rather than waiting for TTL cleanup. Reauthentication increments tokenVersion, so extending temporary expiry cannot revive a prior signup JWT. Completion inserts users fields authProvider, socialSubject, socialIdentity, generated loginId, name, email, phone, emailSource:'USER', emailVerified:true, phoneVerified:true, profileComplete:true and profileCompletedAt, and atomically consumes both contact verification proofs and the temporary authorization. Generated login IDs are not email addresses. New social users always have role USER and no local password. No automatic linking by email, no provider access/refresh token persistence, and no provider tokens or subjects in public/member responses. Legacy local users without authProvider are shown as LOCAL and complete; social users are complete only when profileComplete is Boolean true.

Completed members with at least one usable contact claim `memberIdentityClaimed:true`. Separate partial unique indexes `user_phone_v1` on phone and `user_email_v1` on emailNormalized each apply to claimed documents whose indexed field is a nonempty string, preventing concurrent cross-provider duplication of either contact. Names do not affect duplicate detection. Startup checks all existing completed contacts for duplicates before mutations and backfills normalized contact fields; duplicate keys stop initialization without deleting or merging accounts. Missing legacy email/phone values are preserved, and an email-only legacy admin still claims that email. After both new indexes exist, startup removes the old `user_name_phone_v1` compound index. Pending social users do not claim contacts.

Startup migrates legacy users records only when role=USER, authProvider is GOOGLE/KAKAO and profileComplete is not Boolean true. Reservation, request and reservation-event references are checked before migration; any references stop initialization and preserve the records. A valid provider identity is copied into temporary social_signups and its legacy pending users document removed within one transaction. Completed members and admins are excluded. Old pending member JWTs cannot authenticate after this transition; the user must authenticate with the provider again.

`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `KAKAO_CLIENT_ID` (REST API key), `KAKAO_CLIENT_SECRET` stay in ignored local settings or server-side deployment environment variables. Google requests openid only; Kakao requests no additional personal-data scope and does not need business-app/email permission for this design. Both providers are used only for stable account identity, while name/email/phone are collected by our signup form. `APP_FRONTEND_URL` defaults to http://127.0.0.1:5174 and `APP_BACKEND_URL` to http://127.0.0.1:18081. Both use the same hostname for the exchange cookie. Vercel deployment uses HTTPS service URLs and exact registered callbacks while retaining local callbacks. Frontend and backend routes share the production origin. See the deployment guide for configuration and verification status.

`SMTP_USERNAME` and `SMTP_PASSWORD` configure Gmail SMTP (`smtp.gmail.com:587`, authenticated STARTTLS); the password stays server-side in ignored local/deployment secrets. `FIREBASE_API_KEY`, `FIREBASE_AUTH_DOMAIN` and `FIREBASE_PROJECT_ID` configure browser phone auth and server project validation; the public client fields are exposed through verification/config. No Firebase service-account secret is needed for ID-token signature validation. Enable Phone, authorize the app origin and allow the intended SMS region. A registered test phone receives no real SMS.

`contactVerificationChallenges`, `contactVerificationProofs`, `contactVerificationLimits` and `phoneVerificationReceipts` each have an expiresAt TTL index named contact_verification_expiry_v1 with expireAfterSeconds=0. Challenge/proof _id values are SHA-256 hashes of random tokens; codeHash is SHA-256(challengeId + ':' + code), never the raw code. Challenges live five minutes, proofs ten. Limits store hashed email/address scope keys and fixed-window counts or a 60-second availableAt cooldown. Phone receipts store only SHA-256(Firebase subject + ':' + auth_time) and a 15-minute expiry, preventing token re-exchange. Proofs carry purpose/channel/contact/userId/tokenVersion/createdAt/expiresAt; anonymous signup uses empty userId and version zero. Proofs and challenges are rejected by expiry predicates independently of delayed TTL cleanup. Bound proofs are consumed once with the associated account transaction; raw provider ID tokens are not persisted.

## Frontend
Korean, calm teal/blue hospital product. All real behavior connected to /api (Vite proxy 18081). Pages main/search, consultation, hospital detail/booking, my reservations, admin, login/register. Accessible, responsive. User sees simulation indicator and evidence source/date. Friendly loading/errors/empty state. TanStack Query. No fake successful booking or silent API fallback. No secrets in frontend. No requirement to use generated images.

Hospital detail embeds Kakao Maps using the public `VITE_KAKAO_MAP_JS_KEY` and registered JavaScript SDK domains. Prefer valid HIRA coordinates; otherwise resolve the full hospital address with the SDK services geocoder. Ambiguous/unresolved addresses do not get an invented marker: offer a hospital-name/address search link. Valid coordinates retain external Kakao Maps directions even if the embedded map fails. SAMPLE hospitals have no real map, directions or search link. The app does not collect browser geolocation or store geocoding results in MongoDB. Directions open Kakao Maps rather than calculating routes in this app. Map activation/domain settings and OAuth callback registration are separate.

## Shared deployment state

`oauth_authorization_requests` stores only required OAuth protocol fields with a five-minute expiry; state and browser binding are SHA-256 hashes. Google nonce/PKCE fields are restored for Spring validation. The `hospital_oauth_binding` cookie is HttpOnly, Secure for HTTPS, SameSite=Lax, path `/login/oauth2/code`, max age 300 seconds. `social_login_tickets` has a 60-second expiry. Both collections have zero-second expiresAt TTL indexes and use expiry predicates with atomic findAndRemove, so a different service instance can finish the flow without replay. Provider access/refresh tokens and personal profile attributes are not persisted.

`chat_usage` stores an HMAC-SHA256 key derived from JWT_SECRET, the KST calendar date and caller identity, a count and expiry at the next KST midnight. It shares the existing daily limits of 20 anonymous/60 authenticated calls across instances using conditional atomic increments. It stores no original IP, user ID or symptom text; the former JVM-map key-count limit is removed.

## Verification scope

The contact verification UI makes verified email and phone inputs read-only with the same locked-input colors so the displayed contact stays bound to its verification proof.

Record the current JUnit/build/CI/deployment results in the associated PR rather than carrying forward earlier test counts. Personal verification tests use mocked providers or synthetic proofs in disposable loopback databases; UI verification uses mocked API responses. Gmail SMTP authentication returned 235, which verifies credentials but does not demonstrate message delivery. The production authorized domain and removal of the test phone entry were observed; the user reported saving the KR SMS region policy. Actual verification email/SMS receipt and full real-account flows remain separate checks. See [deployment guide](../infra/README.md).
