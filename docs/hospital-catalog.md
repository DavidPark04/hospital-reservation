# 병원 기본 목록 운영

웹의 병원 검색·홈 목록·AI 추천은 기획서의 병원 기본 정보 컬렉션인 MongoDB `hospitals`를 조회합니다. 사용자가 접속하거나 검색할 때 기본 공공 API 수집을 시작하지 않습니다. 병원 기본 자료는 요일별 지역 수집으로 준비하며, 실제 저장 완료 건수는 실행 결과에서 확인합니다.

## 수집 범위

사용 API는 [건강보험심사평가원 병원정보서비스](https://www.data.go.kr/data/15001698/openapi.do)의 `hospInfoServicev2/getHospBasisList`입니다.

1. 기본 API의 `sidoCd`를 지정해 이번 실행의 지역코드를 하나씩 조회하고, 각 지역의 모든 페이지를 수집합니다. 조건 없는 전국 조회는 사용하지 않습니다.
2. 대상 지역에서 같은 기본 API에 `dgsbjtCd`를 함께 지정해 서비스가 지원하는 16개 진료과의 소속 병원을 확인합니다.
3. 각 지역의 기본 목록과 16개 진료과 소속을 모두 검증한 뒤 원본 `ykiho`로 합쳐 그 지역의 수집 파일을 만듭니다. 완성된 지역은 독립적으로 반영하고, 미완성 지역은 기존 DB를 유지합니다.
4. DB 적용도 검증된 수집 파일에 명시된 지역으로 제한합니다. 해당 지역에서 빠진 병원만 비활성화 후보로 삼고, 수집하지 않은 지역의 자료는 그대로 보존합니다. 기본·진료과 내용이 같은 병원은 다시 쓰지 않습니다.

지원하는 지역코드는 `110000`, `210000`, `220000`, `230000`, `240000`, `250000`, `260000`, `310000`, `320000`, `330000`, `340000`, `350000`, `360000`, `370000`, `380000`, `390000`, `410000`입니다. API에서 더 이상 사용하지 않는 코드는 0건일 수 있으므로, 이번 대상 코드가 모두 검증되었는지와 실제 행의 `sidoCd`가 요청 코드와 같은지를 확인합니다. `240000` 광주 별도 코드는 0건이어도 조회·검증하며, 원본 `360000`의 지역명은 `전남광주`입니다. 기존 DB에 있던 대상 지역이 수집 결과에서 통째로 사라지는 경우는 별도 보호 검사로 중단합니다.

요일별 분할은 각 지역을 주 1회 갱신하는 방식입니다. 지역별 건수 확인과 일요일 재처리에도 호출이 사용됩니다. 각 지역의 조회 시각은 다를 수 있으며, 병원 컬렉션·필드·ID·인덱스와 웹의 DB 조회 방식은 그대로 유지합니다. 수집기는 원래 요일·지역·주 시작일을 필수로 받고, 지역을 생략한 전국 수집 명령은 제공하지 않습니다. 기존 전국 수집 파일의 DB 적용 호환성은 유지합니다.

지원 분류는 내과·신경과·정신건강의학과·외과·정형외과·신경외과·산부인과·소아청소년과·안과·이비인후과·피부과·비뇨의학과·재활의학과·가정의학과·치과·한방내과입니다. 진료과 조건별 목록을 수집하는 것은 병원별 상세 API 호출과 다릅니다.

`의료기관별상세정보서비스`의 진료과·특수진료·전문병원 지정 3종은 예약 수집 대상이 아닙니다. 사용자가 병원을 선택하면 기존처럼 필요한 상세 정보를 조회하며, 완전한 응답은 1시간 재사용합니다. 기본 목록 수집이 상세 API 11종 전체 수집을 의미하지 않습니다.

## 저장과 공개

| 저장소 | 역할 |
| --- | --- |
| `hospitals` | 기획서의 병원 기본 정보: 전체 기본 원본 `apiFields`, 검색 필드, `departmentCodes`, `departments`, `active`, 내용 비교 해시 |
| `hospitalDetails`, `hospitalEvidence` | 선택한 병원의 상세 캐시·근거와 기존 예약·의료진의 참조 |
| `hospitalImportRuns` | 실행별 대상 지역·상태·건수, 지역별 마지막 성공과 역적용 방지 기준, 전국 수집 기준, 동시 적용 방지 잠금, 주·요일·모드별 중복 실행 방지 기록 |

병원 ID는 기존 앱과 같은 `UUID.nameUUIDFromBytes(UTF-8("HIRA:" + ykiho))` 규칙을 사용합니다. `hospitalDetails`는 기획서 이후 추가한 상세 캐시용 보조 컬렉션이며, `hospitals`의 기본 목록을 전부 복제하지 않습니다. 두 컬렉션은 같은 병원 ID를 사용합니다. 웹에서 공개하는 병원 응답에는 원본 전체 필드·암호화 기관번호·비교용 해시를 넣지 않습니다.

`basicSourceHash`는 정렬한 기본 원본 필드의 SHA-256이고, `catalogHash`는 기본 해시와 정렬한 진료과 소속으로 계산합니다. 신규 병원은 추가하고, 해시나 활성 상태가 달라진 문서만 갱신합니다. 진료과 소속만 달라지면 같은 기본 필드·기본 조회 시각을 다시 쓰지 않습니다. 내용이 같은 문서는 날짜만 갱신하지 않으므로 `basicFetchedAt`과 전체 동기화 성공 시각은 다를 수 있습니다.

검증한 대상 지역의 전체 목록에서 빠진 병원은 `active:false`로 바꾸고 `retiredAt`을 남깁니다. 수집하지 않은 지역의 병원이 이번 파일에 없다는 이유로 비활성화하지 않습니다. 비활성화는 현재 원본 목록에서 확인되지 않는다는 뜻이며 폐업 판정이 아닙니다. 다시 나타나면 활성화합니다. 회원·예약·의료진과 과거 이력은 삭제하지 않습니다.

지역별 수집을 모두 검증한 뒤 그 지역의 DB 변경분을 순서대로 적용하며 반영된 자료는 이후 웹 조회에 사용됩니다. 전체 DB를 한 번에 교체하는 트랜잭션은 아닙니다. DB 쓰기 도중 실패하면 일부 변경이 반영될 수 있습니다. 이때 API를 다시 수집하는 대신 유효한 검증 파일과 실행 기록을 확인해 DB 적용만 복구합니다. 요일별 수집 워크플로를 다시 실행해도 이미 사용한 주·요일·모드의 요청은 반복하지 않습니다.

## 기존 컬렉션 이름 전환

이전 버전의 DB를 새 버전과 함께 사용할 때 한 번 실행하는 절차입니다. 병원 기본 정보를 기획서의 `hospitals` 이름으로 맞추며, 기존 문서를 다시 수집하거나 복제하지 않고 컬렉션 이름만 순서대로 변경합니다.

| 이전 이름 | 전환 후 이름 | 자료 |
| --- | --- | --- |
| `hospitals` | `hospitalDetails` | 선택한 병원의 상세 캐시와 샘플 |
| `hospitalBasicCatalog` | `hospitals` | 전국 병원 기본 정보 |

`_id`, 병원 참조와 인덱스를 유지합니다. `hospitalEvidence`, 회원, 의료진, 일정, 예약, 수집 실행 기록의 이름과 자료는 이 작업에서 변경하지 않습니다. 전환 도구는 [rename-hospital-collections.mjs](../scripts/rename-hospital-collections.mjs)입니다.

1. 새 코드의 검사·빌드를 완료하고, 예약 수집 워크플로가 전환 중 새로 시작하지 않도록 중지합니다. 실행 중인 수집은 종료될 때까지 기다립니다.
2. Vercel 운영 트래픽을 일시 정지하고 같은 DB에 연결한 로컬 서버·다른 배포·수동 작업도 중지합니다. 이미 실행 중인 요청과 DB 작업이 끝났는지 확인합니다. 고정된 시간만 기다린 것으로 종료를 판단하지 않습니다.
3. 대상 DB가 포함된 `MONGODB_URI`를 현재 셸의 환경변수로 전달하고 아래 계획 확인 명령을 실행합니다. 계획 파일이 없으면 현재 두 컬렉션의 UUID·문서 수·인덱스 수와 정의 해시를 고정해 저장하며, 이미 있으면 그 계획과 현재 상태를 대조합니다. `--database`는 URI의 실제 DB명을 확인하는 값입니다.

```bash
node scripts/rename-hospital-collections.mjs --database MediPick --plan .runtime/hospital-collection-rename-plan.json
```

4. 트래픽·작업 중지가 유지된 상태에서 같은 계획으로 적용합니다. `--writers-stopped`는 운영자가 중지를 확인했다는 표시이며 도구가 서버나 워크플로를 중지해 주지는 않습니다.

```bash
node scripts/rename-hospital-collections.mjs --database MediPick --plan .runtime/hospital-collection-rename-plan.json --apply --writers-stopped
```

5. 같은 정지 구간에 새 버전을 배포합니다. 배포와 DB 이름 전환의 선후는 바꿀 수 있지만 둘 다 완료되기 전에는 트래픽이나 수집을 재개하지 않습니다. 새 서버는 구형 컬렉션 구성이 남아 있으면 시작을 거절합니다.
6. 같은 계획 확인 명령으로 `state: current`, `basic: hospitals`, `details: hospitalDetails`와 기존 UUID·문서 수·인덱스 일치를 확인합니다. 트래픽을 재개한 뒤 `/api/health`, 병원 검색·상세, 기존 예약 조회를 확인하고 예약 수집 워크플로를 다시 활성화합니다. 아래 요일별 한국 시간 00시 일정과 변경분 저장 방식을 사용합니다.

계획 파일은 이름 전환 대상을 고정하는 메타데이터이며 DB 백업은 아닙니다. DB 백업·계획 파일·운영 로그는 Git에 올리지 않고 따로 보관합니다.

각 이름 변경에는 `dropTarget:false`를 사용합니다. 두 이름 변경 전체가 하나의 트랜잭션은 아니므로 첫 단계 뒤 실패하면 `hospitalBasicCatalog`와 `hospitalDetails`가 함께 있는 중간 상태가 될 수 있습니다. 이때 트래픽·작업 중지를 유지하고 같은 적용 명령과 계획 파일로 재실행하면 남은 단계부터 이어집니다. 완료 상태에서 재실행하면 문서를 다시 옮기지 않습니다.

구버전으로 복구해야 하면 트래픽·작업 중지를 유지하고 같은 계획으로 다음 명령을 실행합니다.

```bash
node scripts/rename-hospital-collections.mjs --database MediPick --plan .runtime/hospital-collection-rename-plan.json --rollback --apply --writers-stopped
```

`state: legacy`를 확인하고 구버전 코드를 복구한 뒤 트래픽·수집을 재개합니다. 전환·복구 중에는 대상 컬렉션을 삭제하거나 덮어쓰지 않습니다. 계획과 UUID·문서 수·인덱스가 달라지면 중단하므로, 운영 재개 후 자료가 변한 상황에서 계획 파일을 새로 만들어 검사를 우회하지 말고 실제 변경과 복구 대상을 먼저 확인합니다.

## 한국 시간 자정의 정규 수집과 일요일 재처리

[Hospital basic catalog sync](../.github/workflows/hospital-catalog-sync.yml)는 기본 브랜치 `main`의 코드로 아래 작업을 수행합니다. 모든 예정 시각은 **한국 시간 00:00**입니다. 월~토는 정규 지역 수집, 일요일은 같은 주의 실패 요청만 한 번 재처리합니다.

| 한국 요일 | 갱신 지역과 HIRA 코드 | UTC cron |
| --- | --- | --- |
| 월 | 서울 `110000` | `0 15 * * 0` |
| 화 | 경기 `310000` | `0 15 * * 1` |
| 수 | 부산 `210000`·전남광주 `360000`·경남 `380000` | `0 15 * * 2` |
| 목 | 대구 `230000`·인천 `220000`·경북 `370000` | `0 15 * * 3` |
| 금 | 전북 `350000`·충남 `340000`·대전 `250000` | `0 15 * * 4` |
| 토 | 충북 `330000`·강원 `320000`·울산 `260000`·제주 `390000`·세종 `410000`·광주 별도 `240000` | `0 15 * * 5` |
| 일 | 같은 주 월~토의 실패 요청만 1회 | `0 15 * * 6` |

한국 자정은 전날 UTC 15시입니다. 일곱 cron을 각각 등록하고 [요일 선택기](../scripts/hospital-catalog-schedule.py)가 `github.event.schedule`의 원래 cron을 요일에 대응시킵니다. 실행이 지연되거나 재실행되어도 원래 요일의 지역을 유지합니다. 알 수 없는 cron이나 요일 입력은 수집 전에 중단합니다. 재처리는 실제 한국 날짜가 일요일일 때만 가능하므로 일요일 작업이 월요일로 지연되면 건너뜁니다. 일요일에 월~토 정규 수집을 선택한 경우도 API 호출과 DB 실행 기록 생성 전에 건너뜁니다.

수동 실행은 GitHub Actions의 **Run workflow → main → day**에서 `monday`~`saturday` 중 수집할 그룹 또는 `sunday` 재처리를 선택합니다. 기본값은 `monday`이며 전체 지역으로 자동 변경하지 않습니다. 수동 실행에도 위의 실제 요일 제한과 주·요일·모드 중복 방지가 적용됩니다. 수정된 코드를 사용할 때는 최신 `main`으로 실행하며, 과거 실행의 재실행은 과거 코드와 요일을 다시 사용한다는 점을 구분합니다.

자정은 실행 예정 시각이며 완료 시각이 아닙니다. GitHub Actions는 부하에 따라 예약 실행이 지연되거나 누락될 수 있고, 공개 저장소에 60일간 활동이 없으면 예약 워크플로가 자동 비활성화될 수 있습니다. 이 경우 워크플로를 다시 활성화하고 수동 실행 결과를 확인합니다. [GitHub 예약 실행 기준](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

워크플로는 `contents: read`, `actions: read` 권한과 한 번에 하나의 실행을 사용하며 기존 실행을 중간 취소하지 않습니다. 실행 제한은 360분입니다. [통합 실행기](../scripts/run-hospital-catalog.py)가 수집·체크포인트 다운로드·중복 방지·DB 적용을 관리합니다. 수집과 DB 반영은 GitHub runner에서 직접 수행하고 Vercel 운영 API·재배포를 사용하지 않습니다. Vercel의 사용자 검색 요청은 여전히 DB 조회를 처리합니다.

저장소 **Settings → Secrets and variables → Actions → Repository secrets**에 아래 두 값을 설정합니다.

| Secret | 용도 |
| --- | --- |
| `HIRA_HOSPITAL_KEY` | 병원정보서비스 사용이 승인된 인증키 |
| `MONGODB_URI` | 대상 DB명이 포함된 Atlas 연결 URI |

이 두 값은 배포용 `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`와 별도입니다. 예약 수집에 상세·OAuth·OpenAI 키는 필요하지 않습니다. Atlas 네트워크 설정에서 해당 실행 환경의 연결이 허용되어야 합니다. 비밀 값과 원본 데이터 파일을 커밋하거나 공개 로그에 출력하지 않습니다.

### 요청별 시도 횟수와 체크포인트

월~토 데이터 페이지는 **500건 고정, 요청마다 1회**만 호출합니다. HTTP 오류·통신 실패뿐 아니라 HTTP 200의 XML 서비스 오류도 실패로 기록하며, 같은 날 즉시 재시도하거나 100건으로 나누어 다시 요청하지 않습니다. 각 지역·진료과의 총건수를 대조하는 1건 조회는 별도로 계획된 검증 요청이며 데이터 페이지의 재시도가 아닙니다. 이 검증 요청도 한 번만 시도합니다. 오류 로그에는 고정된 사유와 검증한 숫자 코드만 남기고 응답 메시지·요청 URL·인증키는 출력하지 않습니다.

주중에는 `.runtime/hospital-catalog/checkpoint/` 아래에 키가 없는 `run.json`과 요일별 `batch.json`, 요청별 성공 응답·실패 기록인 `requests/`, 검증 완료 지역의 `ready/`를 저장합니다. 워크플로는 실패·취소 때도 남아 있는 주중 체크포인트를 `hospital-catalog-checkpoint-<run_id>` 아티팩트로 업로드하며 **14일** 보관합니다. 아티팩트에는 인증키나 DB 접속 정보를 넣지 않습니다. 정상 결과 요약은 루트의 `result.json`에 따로 기록합니다. 일요일 처리 결과는 Actions 요약·로그와 영구적인 재처리 실행 기록으로 확인하며, 재처리 결과를 새 원본 아티팩트로 올리지 않습니다.

일요일에는 같은 저장소·워크플로·`main`에서 생성된 현재 한국 주간의 월~토 수집 아티팩트만 검증해 읽습니다. 주 시작일·원래 요일·지역·페이지 크기를 대조하고 일요일 재처리 아티팩트는 원본으로 다시 사용하지 않습니다. 성공한 응답은 캐시를 재사용하고, 주중에 `failed`로 기록된 요청만 **1회** 재처리합니다. 주중에 호출하지 못한 새 페이지는 일요일에 추가로 호출하지 않습니다. 처음 페이지와 총건수 검증 요청이 모두 실패해 나머지 페이지를 알 수 없었던 경우도 완전한 지역이 되기 전에는 DB를 갱신하지 않습니다.

일요일 재처리가 실패하거나 자료가 여전히 불완전하면 해당 지역의 이번 주 갱신을 종료하고 기존 DB를 유지합니다. 실패를 다음 일요일로 이월하지 않으며 다음 주 정규 요일에 새 수집을 시작합니다. API 성공만으로 적용하지 않고 기본 목록·16개 진료과·건수·중복·지역·해시·조회 시각 검증을 모두 통과한 지역만 적용합니다.

수집 전 MongoDB에 `hospital-basic-batch:<주 시작일>:<원래 요일>:<collect|retry>`를 원자적으로 등록합니다. 같은 키가 이미 있으면 호출을 건너뜁니다. 실행이 중단돼도 기록을 자동으로 지우거나 재시도 권한을 되살리지 않으므로 Actions 재실행이 추가 호출을 만들지 않습니다. `collect`와 일요일 `retry`는 별도 기록입니다.

## 실행과 검증 파일의 DB 적용 복구

정규 수집과 초기 자료 준비는 위 GitHub Actions의 요일별 그룹을 사용합니다. 통합 실행기는 저장소 `main`의 실제 Actions 실행인지 확인하며, 로컬 셸에서 정규 수집을 시작하지 않습니다. 워크플로 내부 명령은 아래와 같습니다. `CATALOG_DAY`는 요일 선택기에서 받은 `monday`~`sunday`이며 사용자가 입력한 셸 문자열을 실행하지 않습니다.

```bash
npm ci --ignore-scripts
python scripts/run-hospital-catalog.py --directory .runtime/hospital-catalog --day "$CATALOG_DAY"
```

Python 3.12와 Node.js 22를 사용하며 `HIRA_HOSPITAL_KEY`, `MONGODB_URI`와 아티팩트 조회용 `GITHUB_TOKEN`을 워크플로 환경변수로 전달합니다. 스크립트는 `.env`를 자동으로 읽지 않습니다. 데이터 수집과 별도 총건수 검증 요청은 동시 최대 2개, 실행 전체 호출 예산은 최대 10,000회이며 계정의 실제 승인 한도를 늘리는 설정이 아닙니다. 일요일에도 모든 배치가 같은 호출 예산을 나눠 씁니다.

주중 수집 파일은 완성된 지역마다 `checkpoint/<원래 요일>/ready/<지역코드>/catalog.jsonl`, `catalog-manifest.json`으로 생성됩니다. 주중 파일은 `schemaVersion: 3`, `scope: regions-with-department-memberships`, 명시적인 `regions`와 정확히 일치하는 `regionScopes`를 포함합니다. 일요일 재처리 파일은 내려받은 원본 배치 폴더의 `ready/<지역코드>/`에 생성하며 버전 4와 별도의 `recovery` 정보를 사용합니다. 기존 버전 1·2의 전국 수집 파일도 DB 적용 도구가 검증해 읽을 수 있습니다. 이는 수집 파일 형식이며 병원 문서 스키마를 바꾸지 않습니다.

DB 쓰기만 복구할 때는 보관한 아티팩트에서 해당 지역의 검증 파일을 준비합니다. `MONGODB_URI`를 현재 셸의 환경변수로 전달하고 아래처럼 비교한 뒤 적용합니다. `--apply` 없는 명령은 DB와 비교한 계획만 출력하며 공공 API를 호출하지 않습니다. 예시는 월요일 서울 파일입니다.

```bash
node scripts/sync-hospital-catalog.mjs --directory .runtime/hospital-catalog/checkpoint/monday/ready/110000
node scripts/sync-hospital-catalog.mjs --directory .runtime/hospital-catalog/checkpoint/monday/ready/110000 --apply
```

DB 명령은 체크섬·대상 지역별/전체 건수·진료과 범위·조회 시각을 다시 검증합니다. 파일의 모든 병원은 선택된 지역에 속해야 하고 지역별 합계는 파일 전체 합계와 일치해야 합니다. 일반 버전 1·2·3은 48시간보다 오래된 수집 파일을 적용하지 않습니다. 일요일 전용 버전 4는 `recovery.mode: sunday-failed-requests`, `attempt: 1`, 원래 요일의 지역 범위와 동일 주간을 검사하며, 최초 조회 후 최대 8일·일요일 완료 후 최대 48시간까지만 검증·적용할 수 있습니다. `completedAt`과 `recoveredAt`은 같은 일요일 시각이어야 합니다. 일요일 이후 새 API 재처리를 허용한다는 뜻은 아닙니다. 이 제한은 새로 적용할 파일의 제한이며 기존 DB 자료를 지우거나 만료시키는 기준이 아닙니다. 원래 자료가 없는 코드만 선택한 지역 수집은 검증된 0건 파일을 만들 수 있지만, 전국 수집 결과가 모두 0건이면 중단합니다.

## 확인과 복구

- Actions 실행 요약과 루트 `result.json`의 `day`, `mode`, `weekStartKst`, `completeRegions`, `deferredRegions`, `requests`, `skipped`, 요일별 `batches`를 확인합니다. 배치별 `claimed`, `failedRequests`, `skippedRequests`, `appliedRegions`로 실제 처리 범위를 구분합니다. 완성된 지역의 `sync-result.json`에서는 `rows`, `inserted`, `updated`, `reactivated`, `retired`, `unchanged`, `verified`를 확인합니다. 지역 수집 건수는 해당 실행 범위이며 전국 DB 총건수가 아닙니다.
- `hospitalImportRuns`에는 실행 UUID의 `COMPLETE` 또는 `FAILED` 상태를 기록합니다. `hospital-basic-region-current:<지역코드>`는 그 지역의 마지막 성공, `hospital-basic-region-high-water:<지역코드>`는 적용을 시작한 최신 수집본의 기준입니다. 일부 반영 후 실패해도 해당 지역에 더 오래된 자료를 덮어쓸 수 없습니다. 서로 다른 지역의 독립적인 수집 시각은 불필요하게 충돌시키지 않으며, 같은 기관번호가 다른 지역으로 이동한 경우에는 현재 지역의 최신 기준도 확인해 이전 지역으로 되돌리지 않습니다.
- `hospital-basic-current`와 `hospital-basic-high-water`는 전국 수집의 기존 기준으로 유지하며 전국 전체를 적용할 때만 갱신합니다. `hospital-basic-last-run`에는 지역·전국 구분 없이 마지막 성공 실행의 대상 지역·건수·시각을 기록합니다. `hospital-basic-sync-lock`은 모든 DB 적용이 함께 사용하는 임시 잠금입니다.
- 누락 페이지·중복 기관번호·총건수 불일치·분류 범위 불일치·수집 중 지역별 총건수 변경이 있는 지역은 적용하지 않습니다. 다른 지역의 행이 응답되거나 같은 지역의 기본 자료에 없는 기관이 진료과 목록에 나타나도 해당 지역을 보류합니다. 다른 완성 지역은 독립적으로 적용할 수 있습니다.
- 대상 지역의 기존 활성 자료에서 빠진 건수가 `max(100, 대상 기존 활성 건수의 5% 내림)`보다 크면 대량 비활성화를 중단합니다. 대상 지역별로 지역 전체 누락 또는 `max(5, 해당 지역 활성 건수의 5% 내림)` 초과 누락도 검사합니다. 수집 파일에서 같은 병원 ID가 다른 대상 지역으로 옮겨진 경우는 누락으로 세지 않습니다. 실제 원본 변화인지 확인한 뒤 수집 범위와 자료를 검토하며, 한 번 실패했다는 이유로 DB를 비우지 않습니다.
- 예약 수집의 성공 응답·실패 기록은 14일간 아티팩트로 보관하지만 재처리 대상은 현재 주의 원래 실패 요청뿐입니다. 중복 실행 방지 기록을 삭제해 다시 호출하거나 과거 주의 실패를 새 주로 이월하지 않습니다. 보관 기간은 API 재시도 가능 기간과 다릅니다.
- 수집 실패는 웹의 실시간 기본 API 조회로 전환하지 않습니다. DB 적용 실패는 유효한 검증 자료를 확인한 뒤 `sync-hospital-catalog.mjs --directory <검증 파일 폴더> --apply`로 적용만 복구하고 `COMPLETE`와 최종 검증 건수를 확인합니다. 해당 주의 수집 워크플로 재실행은 중복 실행을 건너뛰므로 DB 복구 명령과 다릅니다. 회원·예약·상세 캐시를 초기화하지 않습니다.

코드·테스트 통과, 실제 초기 적재, 예약 실행의 첫 성공, 운영 웹 반영은 별도 확인 항목입니다. 문서나 워크플로 파일이 추가됐다는 사실만으로 운영 저장·스케줄 실행이 완료됐다고 판단하지 않습니다.
