# API 계약 — 설계 초안

현재 엔드포인트는 구현되지 않았습니다. [기준 기획서](https://app.notion.com/p/879b8822a70f82f789298129ce73194d)의 흐름 예시인 `POST /api/chat`, `POST /api/reservations`를 반영합니다. 아래 나머지 경로·요청·응답은 FE/BE가 Issue #3에서 확정할 제안입니다. 기본 경로는 `/api`입니다.

| 기능 | 메서드·경로 제안(`/api` 기준) | 권한 |
| --- | --- | --- |
| 회원가입 | POST `/auth/signup` | 비회원 |
| 로그인·로그아웃 | POST `/auth/login`, POST `/auth/logout` | 로그인은 비회원, 로그아웃은 회원 |
| 병원 검색·상세 | GET `/hospitals`, `/hospitals/{id}` | 전체 |
| 상담 조건 추출·추가 질문 | POST `/chat` | 전체, 사용량 제한 검토 |
| 가상 의료진·시간표 | GET `/hospitals/{id}/doctors`, `/doctors/{id}/slots` | 전체 |
| 예약 생성 | POST `/reservations` | 회원 |
| 내 예약 | GET `/me/reservations` | 본인 |
| 예약 변경·취소 | PATCH `/reservations/{id}`, POST `/reservations/{id}/cancel` | 본인 |
| 관리자 일정·정원·휴진 | POST `/admin/slots`, PATCH `/admin/slots/{id}` | 관리자 |

각 엔드포인트에 요청·응답 JSON, 필드 타입, 필수 여부, JWT 인증 방식, HTTP 상태·오류 코드를 적습니다. 페이지 처리, UTC 날짜·시간 전송과 한국 시간 표시, 빈 결과·외부 API 장애 표시를 통일합니다. JWT 만료·갱신·로그아웃 시 토큰 처리 방식은 구현 전 합의합니다.

## 예약 계약 기준

- 예약 생성에는 `Idempotency-Key`를 전달하고 서버는 사용자·키·요청 본문을 함께 확인합니다. 동일 키·동일 본문은 기존 응답, 동일 키·다른 본문은 `409`입니다.
- `requests.requestHash` 계산 방식, 키 보관 기간, 변경·취소의 재시도 계약은 Issue #3에서 확정합니다.
- 활성 예약은 `RESERVED`, 취소는 `CANCELED`입니다. 일정 변경은 이벤트 `CHANGE`로 기록하며 `CHANGED` 상태를 만들지 않습니다.
- 생성·변경·취소 모두 서버에서 사용자 소유권과 참조 ID를 확인합니다. 정원 부족·휴진·중복 예약·권한 오류·트랜잭션 실패를 각각 구분해 명세합니다.
- 관리자 일정·정원·휴진 관리는 필수입니다. 전체 예약·회원 관리 도구는 시험 이후 확장입니다.

구체적인 컬렉션·인덱스·트랜잭션 경계는 [DB 설계](database.md)를 따릅니다.

## 외부 정보와 실패 처리

AI는 조건 정리·추가 질문·추천 사유 작성에 사용합니다. 서버가 실제 조회한 병원·근거만 응답에 포함하고 출처·기준 기간·조회 시각을 구분합니다. 실제 병원 정보와 가상 의료진·일정을 함께 보여 줄 때 모의 예약임을 표시합니다.

AI 실패 시 직접 검색으로 진행합니다. 병원 API 실패 시 마지막 정상 캐시와 확인일 또는 재시도 안내를 전달합니다. 증상 원문은 기본 저장하지 않습니다. 공공 API 승인·실제 응답은 11/25, AI 연동 여부는 12/2에 확인하고 미연동 항목을 결과보고서에 남깁니다.

프론트엔드는 합의한 모의 응답으로 먼저 구현할 수 있으며 실제 서버 연동 완료 여부를 별도로 기록합니다.
